# Ошибка nginx: connect() failed (13: Permission denied)

## Исходная ошибка

```
connect() to 192.168.133.22:8001 failed (13: Permission denied) while connecting to upstream,
client: 62.89.208.14, server: api-driver-3taxi.gram.tj,
request: "POST /api/mob-app/order/finish HTTP/2.0",
upstream: "http://192.168.133.22:8001/api/mob-app/order/finish",
host: "api-driver-3taxi.gram.tj"
```

## Что это значит

Nginx получил запрос `POST /api/mob-app/order/finish` и попытался проксировать его на upstream `192.168.133.22:8001` (`proxy_pass`), но системный вызов `connect()` вернул код **13 — Permission denied**.

Это **не** "Connection refused" (код 111 — порт закрыт/сервис не слушает) и **не** таймаут. Код 13 означает, что операционная система (или средство мандатного контроля доступа) **запретила** самому nginx открывать это сетевое соединение, хотя порт может быть открыт и сервис на 8001 — рабочим.

## Наиболее вероятные причины

1. **SELinux** (если используется на сервере) — самая частая причина именно такой формулировки ошибки. Политика `httpd_can_network_connect` по умолчанию выключена и блокирует nginx/httpd от исходящих соединений на нестандартные порты.

   Проверить:
   ```bash
   getenforce
   ```
   Если `Enforcing`:
   ```bash
   sudo setsebool -P httpd_can_network_connect 1
   ```
   Если порт 8001 нестандартный, может понадобиться:
   ```bash
   sudo semanage port -a -t http_port_t -p tcp 8001
   ```

2. **Firewall с явным REJECT** (iptables/ufw/nftables/security group облака) между nginx-сервером и `192.168.133.22`. В отличие от DROP (даёт таймаут), REJECT с `icmp-*-prohibited` на Linux транслируется ядром в **EACCES (Permission denied)**, а не в ECONNREFUSED. Нужно проверить правила firewall/security group как на самом nginx-сервере, так и на пути к `192.168.133.22` (если это отдельная VM/контейнер в облаке или k8s NetworkPolicy).

3. **AppArmor** — если на сервере включён кастомный профиль AppArmor для nginx, ограничивающий сетевые соединения (реже, чем SELinux, но встречается на Ubuntu).

4. **Docker/k8s** — nginx-контейнер может не иметь маршрута/разрешения в сегмент сети `192.168.133.22` из-за network policy или неправильной сетевой конфигурации.

## Как продиагностировать

С сервера, где стоит nginx:

```bash
getenforce                                            # проверить SELinux
sudo ausearch -m avc -ts recent                       # если SELinux — покажет denial-записи
curl -v http://192.168.133.22:8001/                   # проверить доступность вручную, от root
sudo -u www-data curl -v http://192.168.133.22:8001/  # от имени пользователя nginx — часто именно тут видна разница
sudo iptables -L -n -v                                # локальный firewall
sudo ufw status verbose                                # если используется ufw
```

Если `curl` от root проходит, а от `www-data`/`nginx` — нет, это почти гарантированно SELinux/AppArmor. Если не проходит вообще ни от кого — смотреть firewall/security group между машинами.

## Что проверить на самой ВМ 192.168.133.22 (backend, порт 8001)

Ошибка `13: Permission denied` возникает на стороне nginx, но её причина может быть создана и настройками backend-сервера. На ВМ `192.168.133.22` нужно проверить:

### 1. Слушает ли сервис порт 8001 и на каком интерфейсе

```bash
sudo ss -tlnp | grep 8001
```

Важно смотреть **на каком адресе** висит порт:
- `127.0.0.1:8001` — сервис слушает только локально и **не примет** соединение снаружи (с nginx-сервера), даже если порт "открыт". Нужно перебиндить на `0.0.0.0:8001` или на конкретный IP `192.168.133.22`.
- `0.0.0.0:8001` или `192.168.133.22:8001` — сервис доступен снаружи, проблема не в биндинге.

### 2. Работает ли сервис вообще

```bash
sudo systemctl status <имя-сервиса>
sudo journalctl -u <имя-сервиса> -n 100 --no-pager
```
Если сервис в цикле падает/перезапускается, соединения могут периодически рваться.

### 3. Локальный firewall на этой ВМ (iptables/ufw/nftables)

```bash
sudo iptables -L -n -v
sudo ufw status verbose
sudo nft list ruleset      # если используется nftables
```
Ищем правила, которые блокируют входящие соединения на 8001 именно с IP nginx-сервера. Обратите внимание на **REJECT** (даёт EACCES на стороне клиента через ICMP prohibited) в отличие от DROP (даёт таймаут).

### 4. SELinux/AppArmor на самой ВМ (если это отдельный сервис, а не сам nginx)

```bash
getenforce
sudo aa-status   # если AppArmor
```
Может блокировать не только nginx, но и backend-процесс от прослушивания/приёма соединений на нестандартном порту.

### 5. Проверка доступности порта именно с nginx-сервера (а не локально на самой ВМ)

С сервера nginx (не с самой ВМ 192.168.133.22!):
```bash
telnet 192.168.133.22 8001
# или
nc -zv 192.168.133.22 8001
# или
curl -v http://192.168.133.22:8001/
```
Если это не проходит именно отсюда, а локально на ВМ (`curl -v http://127.0.0.1:8001/` или `curl -v http://192.168.133.22:8001/` с самой ВМ) работает — проблема в сети/firewall между машинами, а не в самом сервисе.

### 6. Security Groups / облачный firewall

Если ВМ находится в облаке (AWS/GCP/Yandex Cloud/VK Cloud и т.п.) или в изолированном сегменте (VPC/подсеть), проверить правила Security Group / Network ACL на разрешение входящего трафика на TCP 8001 с IP nginx-сервера.

### 7. Логи самого backend-приложения

Если соединение до сервиса технически доходит (firewall и биндинг в порядке), но сервис сам отвечает ошибкой авторизации/прав на уровне приложения — стоит проверить логи приложения на 8001 в момент запроса `POST /api/mob-app/order/finish`, возможно проблема не сетевая, а в самом приложении (хотя формулировка "(13: Permission denied)" в лог nginx пишется именно об ошибке `connect()`, а не об ответе приложения — так что это менее вероятно, но стоит исключить).

### Итоговый чек-лист для ВМ 192.168.133.22

- [ ] `ss -tlnp | grep 8001` — сервис слушает на правильном интерфейсе (не только 127.0.0.1)
- [ ] `systemctl status` — сервис запущен и стабилен
- [ ] `iptables`/`ufw`/`nftables` — нет REJECT/DROP правил для порта 8001 с IP nginx-сервера
- [ ] `getenforce`/`aa-status` — SELinux/AppArmor не блокирует сервис
- [ ] Проверка `telnet`/`nc`/`curl` с nginx-сервера на `192.168.133.22:8001` — не проходит именно отсюда
- [ ] Security Group / облачный firewall разрешает входящий TCP 8001 с IP nginx-сервера
